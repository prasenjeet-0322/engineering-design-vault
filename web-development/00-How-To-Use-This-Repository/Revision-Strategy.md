# 🔄 Revision Strategy: Retaining Engineering Knowledge

Engineering knowledge decays quickly if not actively used. This repository is built not just for initial learning, but for **rapid retrieval and long-term retention**.

## 1. Active Recall over Passive Reading
Never just "read" through your notes. Use the structures built into this repository to test yourself. 

- **Look at the H1/H2 Headers:** Cover the content below the header (e.g., "What problem does X solve?"). Try to answer it aloud before reading the explanation.
- **Use the "Predict the Output" sections:** Treat these like mini-tests. Write down your predicted output before scrolling down to the answer.
- **Use the "Revision Summary":** Every Level 3 topic ends with a TL;DR summary. Try to recite the full 15 points *just* by looking at the summary.

## 2. Spaced Repetition (The System)
Integrate these notes with a spaced repetition system (like Anki) or simply cycle through folders on a schedule.
- **Day 1:** Learn the concept (Read Level 1 & 2).
- **Day 3:** Attempt the "Debugging Scenarios" and "Predict the Behavior" sections.
- **Week 2:** Explain the "Engineering decision-making" (Tradeoffs) out loud.
- **Month 1:** Review only the "Revision Summary".

## 3. The Feynman Technique
If you cannot explain a concept from this vault simply, you don't understand it well enough.
- Use the **Mental Models** provided in Level 1 to explain concepts to imaginary junior developers.
- Focus heavily on the "Why?" (Level 2). Knowing *how* to write a `useEffect` is easy; explaining *why* it causes an infinite loop requires deep understanding.

## 4. When Preparing for Interviews
1. Start with the **Revision Summaries**.
2. Immediately jump to the **Engineering Decision-Making** (Tradeoffs) and **Comparison with alternatives**. Interviewers care far more about *why* you chose a tool over *how* to write its syntax.
3. Review the **Common Mistakes**—these make for excellent talking points when discussing past projects ("One issue we ran into was X, because...").
