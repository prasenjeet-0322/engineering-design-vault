## 01 — ⚡ 30-Second Executive Cheat Sheet

The core problem: Accessibility is not complete merely because `<button aria-label="Delete">` exists. A keyboard user must also be able to reach it, activate it, and not get trapped.

### The 4 Pillars of Keyboard Accessibility:
1. **Reachability (The Tab Order):** Can I get to it?
2. **Operability (The Interaction):** Can I activate it using Enter/Space or Arrow keys?
3. **Visibility (The Focus Ring):** Do I know where I am?
4. **Predictability (Focus Management):** When a modal opens, does focus move to it? When it closes, does focus go back?

## 02 — The DOM Focus Model vs. React Synthetic Events

React abstracts away many DOM events, but focus management heavily relies on real DOM nodes and the browser's native focus system.

### How Browsers Handle Focus
When a user presses `Tab`:
1. The browser computes the "tabbable" elements in the DOM.
2. It moves `document.activeElement` to the next element.
3. It fires `blur` on the old element and `focus` on the new element.

React intercepts these and fires `onBlur` and `onFocus` synthetic events. However, *setting* focus imperatively requires a direct reference to the DOM node (`ref.current.focus()`).

## 03 — Reachability: The Tab Order and `tabIndex`

The `tabIndex` attribute is the primary API for controlling keyboard reachability.

### `tabIndex="0"` (Add to natural tab order)
Makes a non-focusable element (like a `<div>`) focusable and adds it to the natural tab order.
*Warning:* Don't use this to build custom buttons unless you also add keyboard event handlers (Enter/Space) and ARIA roles. Just use `<button>`.

### `tabIndex="-1"` (Programmatic focus only)
Removes the element from the natural tab order, but allows it to receive focus programmatically via JavaScript (`element.focus()`). 
*Crucial for:* Managing focus inside composite widgets (like tabs or menus) and moving focus to a modal dialog container.

### `tabIndex > 0` (Anti-Pattern)
*Never use positive tabIndex.* It creates a nightmare for maintenance and destroys the logical reading order for screen reader users.

## 04 — Visibility: Designing Accessible Focus Rings

A focus ring is a visual indicator that shows which element has keyboard focus. It is non-negotiable for keyboard users.

### The CSS `:focus-visible` Pseudo-class
In modern web development, `:focus-visible` is the standard for styling focus rings. It only shows the focus ring when the user is navigating via keyboard, preventing ugly outlines when clicking with a mouse.

```css
/* Base reset - be careful! */
button:focus {
  outline: none; /* Only do this if you provide a fallback */
}

/* The modern approach */
button:focus-visible {
  outline: 2px solid #2563eb;
  outline-offset: 2px;
}
```

### High Contrast Mode Considerations
Ensure your focus rings are visible in Windows High Contrast Mode. Use `outline` rather than `box-shadow` or `border` where possible, as `outline` is explicitly mapped to system colors in HCM.

### The Basic Pattern

```tsx
import { useRef, useEffect } from 'react';

function FocusInputOnMount() {
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    // We must wait for the DOM to be painted
    inputRef.current?.focus();
  }, []);

  return <input ref={inputRef} type="text" aria-label="Search" />;
}
```

## 06 — Composite Widgets: Roving `tabIndex`

For complex widgets like Tabs, Menus, or Grids, the W3C specifies that the entire widget should only take up *one* stop in the tab sequence. Once inside, users navigate using the Arrow keys.

### The Roving `tabIndex` Pattern
1. Only one item in the widget has `tabIndex={0}`.
2. All other items have `tabIndex={-1}`.
3. When the user presses an arrow key, the React component:
   - Updates state to change which item has `tabIndex={0}`.
   - Programmatically calls `.focus()` on the newly active item.

### React Implementation Example (Tabs)

```tsx
// Simplified conceptual example
const [activeIndex, setActiveIndex] = useState(0);
const refs = useRef<(HTMLButtonElement | null)[]>([]);

const handleKeyDown = (e: React.KeyboardEvent, index: number) => {
  let nextIndex = index;
  if (e.key === 'ArrowRight') nextIndex = index + 1;
  if (e.key === 'ArrowLeft') nextIndex = index - 1;
  
  // Wrap around logic
  if (nextIndex >= tabs.length) nextIndex = 0;
  if (nextIndex < 0) nextIndex = tabs.length - 1;

  if (nextIndex !== index) {
    setActiveIndex(nextIndex);
    refs.current[nextIndex]?.focus();
  }
};
```

## 07 — Composite Widgets: `aria-activedescendant`

An alternative to roving `tabIndex` is `aria-activedescendant`. This is commonly used in Comboboxes (autocomplete dropdowns) or Listboxes where physical focus stays on an input field, but "virtual" focus moves through a list of options.

### The `aria-activedescendant` Pattern
1. Physical focus remains on the container (e.g., `<input>`).
2. The container has `aria-activedescendant="id-of-active-option"`.
3. As the user presses arrow keys, React updates the `aria-activedescendant` ID to point to the currently highlighted option.
4. The highlighted option is visually styled as focused (e.g., using CSS).
5. Screen readers announce the newly highlighted option as if it had received real focus.

### React Implementation Considerations
You must maintain a stable mapping of IDs for the options. Using `React.useId()` is highly recommended here to generate unique prefixes for the option IDs to avoid collisions.

## 08 — Focus Trapping: Modals and Dialogs

When a modal dialog opens, keyboard focus MUST be trapped within it. A user should not be able to Tab out of the modal into the obscured background content.

### The Requirements
1. **Initial Focus:** When the modal opens, focus must move to an element inside it (usually the first interactive element or the dialog container itself if it has `tabIndex={-1}`).
2. **Focus Trap:** Tabbing from the last element should loop back to the first element. Shift+Tabbing from the first element should loop to the last element.
3. **Escape Key:** Pressing `Escape` should close the modal.
4. **Focus Restoration:** When the modal closes, focus MUST return to the element that triggered it to open.

### Building a Focus Trap Hook (`useFocusTrap`)
A robust focus trap queries the DOM for focusable elements using a selector like:
`button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])`

Then, it listens to the `keydown` event for the `Tab` key on the modal container, prevents default behavior if necessary, and manually loops the focus.

## 09 — Focus Restoration: The Return Journey

Focus restoration is often forgotten but is critical for a non-disorienting experience. If focus is lost when a modal closes, it defaults to the `<body>`, forcing keyboard users to start tabbing from the top of the page again.

### The `useFocusRestoration` Pattern
1. Before opening the modal, capture the current focus: `const triggerRef = useRef(document.activeElement)`.
2. When the modal unmounts (or closes), restore focus: `triggerRef.current?.focus()`.

### Edge Cases in React
- What if the trigger element was removed from the DOM? (e.g., deleting an item from a list). You need a fallback strategy (e.g., focus the *next* item in the list, or the container).
- React 18 Concurrent rendering can sometimes cause timing issues with focus restoration; use `useLayoutEffect` if necessary to ensure focus is restored synchronously with the DOM update.

## 10 — Advanced Topic: Dynamic Content & Focus Loss

When an element that currently has focus is removed from the DOM, focus drops to the `<body>`. This is "Focus Loss" and is extremely disorienting.

### Common Scenarios
- Deleting an item from a list while focus is on the "Delete" button.
- Submitting a form that replaces the form with a "Success" message.
- Closing an inline alert.

### The Solution: Predictable Relocation
You must anticipate the removal and move focus *before* or *immediately after* the element is removed.

```tsx
const handleDelete = (id) => {
  // Determine next element to focus (e.g., the previous sibling or the parent container)
  const nextFocusElement = getNextFocusTarget(id); 
  
  removeItemFromState(id);
  
  // Move focus
  nextFocusElement?.focus();
}
```
For a "Success" message replacing a form, ensure the message container has `tabIndex={-1}` and move focus to it so the screen reader announces it immediately.

## 11 — The Stack Context: Managing Multiple Overlays

What happens if a Modal opens, and inside that Modal, a Dropdown Menu opens?

You now have a stack of overlays. 
- Pressing `Escape` should only close the *top-most* overlay (the Dropdown).
- The Focus Trap should only apply to the *top-most* overlay.

### The Global Overlay Stack Registry
Enterprise React applications need an `OverlayManager` or a Context-based stack that tracks active overlays. When an overlay mounts, it pushes itself onto the stack. When it unmounts, it pops itself. ## 12 — Testing Keyboard Navigation

You cannot test keyboard accessibility with a mouse. Put the mouse away.

### Manual Testing Protocol
1. Use `Tab` and `Shift+Tab` to navigate through every interactive element.
2. Verify a clear, highly visible focus ring exists for every stop.
3. Use `Enter` and `Space` to activate buttons and links.
4. Use `Arrow Keys` to navigate composite widgets (Tabs, Menus, Radios).
5. Open every modal and verify the focus trap loops correctly.
6. Close every modal (via Escape and Cancel buttons) and verify focus returns to the trigger.

### Automated Testing
- Use `@testing-library/user-event` instead of `fireEvent`. `userEvent.tab()` simulates real tab sequences.
- Assert focus using `expect(element).toHaveFocus()`.

```tsx
import userEvent from '@testing-library/user-event';

test('modal traps focus', async () => {
  const user = userEvent.setup();
  render(<Modal />);
  
  await user.tab();
  expect(screen.getByRole('button', { name: /close/i })).toHaveFocus();
});
```
